# Stage21A — physical crowns, wallet and contract economy

Date:2026-11-04. Branch dev/0.21.0, base35d5784. Stage21A implementation completed; remaining Stage21 phases not started. This is a development checkpoint, not a0.21.0 RC1/public release.

## Mechanics

Registered witchersbestiary:witcher_crown (stack64) and witchersbestiary:witcher_wallet (stack1), creative Tools entries and RU/EN labels. Original deterministic voxel item models and32px textures are generated by tools/generate-currency.py; no third-party images are embedded. Static models have real thickness/volume. Three leather, one gold ingot and one string craft a wallet; leather unlocks its recipe. Crowns have no free crafting recipe.

WalletComponents.BALANCE is a persisted item component using a nonnegative long codec. Capacity Long.MAX_VALUE. No second balance ledger exists. Wallets can be dropped/transferred like normal items, carrying their component. This is not a Bundle and accepts no nested items. Both hands can open the wallet. Main/offhand wallet storage is supported.

GUI: balance, custom decimal amount, deposit/withdraw1/10/64/all, localized rejection/success. Server requires current handler sync ID, expected operation sequence, exact bound ItemStack reference in its original slot and a living owner. Repeated nonces cannot repeat an operation; moving/replacing/dropping the bound item invalidates the session. No foreign wallet lookup by UUID. Slots are not exposed for container shift-click/drag insertion; normal item transfers occur outside this screen.

WalletTransactions preflights a copied main inventory, validates all amounts/overflow and capacity, then commits on the server thread. Full withdrawal is rejected atomically when physical capacity is insufficient; no money is spawned on the ground. Arithmetic uses CrownBalance. All is bounded by actual coins/balance and capacity, never by creating huge stack collections. Creative/operator item cloning remains privileged vanilla behavior, not an anti-admin security boundary.

CrownPickupMixin applies only on the server to crown ItemEntity collisions, respects vanilla pickup delay and owner, chooses wallets in main-inventory order then offhand, records pickup statistics and decrements each item exactly once. It can use a wallet even with a full physical inventory. Technical overflow remainder uses the normal vanilla pickup path or remains as an item; no wallet means unchanged vanilla pickup.

## Contract economy and migration

CrownRewards.fresh converts emerald grants only when assigning NEW contracts, after procedural snapshot generation. Initial exchange is10 crowns per former emerald, preserving existing relative amounts/XP (legacy three-species Common30/Rare60/Epic100; fixed Swamp Lord120 and Grave Devourer140; other species use their existing threat formula times10). These are the implemented initial balance values, not a claim to match every proposed indicative range.

ContractInstance.fromNbt never performs this conversion. Existing active/completed emerald snapshots retain exactly their original items/amounts, IDs, targets and investigations. Board previews use crowns only for new entries; accepted entries use their immutable snapshots. Rotation/five offers/personal cycles are unchanged.

The existing ContractRewards service plans wallet credits plus physical remainder on copies before consuming the completed reward. Wallets are selected deterministically, including offhand. If delivery cannot fit, nothing is committed and reward stays claimable. Existing owner/completion checks and once-only transitions remain authoritative; no parallel reward history was created.
